# ExaPolymer на Next — инструкция для продолжения работы

Второй кандидат на сайт ExaPolymer. Основа — проект, сгенерированный GPT через OpenAI Sites; поверх накачено то, чем живёт рабочий сайт `exapolymer.ru` (папка `Cloude\Сайт инженерных пластиков`).

**Это отдельный проект для сравнения. Рабочий сайт не трогать** — он остаётся в своей папке и на своём домене. Решение, на чём остановиться, ещё не принято.

## Запуск

```bash
corepack pnpm install     # pnpm не в PATH, поэтому через corepack
corepack pnpm dev         # http://localhost:3000
corepack pnpm build       # производственная сборка
corepack pnpm start       # прод-сервер поверх dist/
```

Node ≥ 22.13. Редактор каталога — `http://localhost:3000/editor/` — **только в `pnpm dev`**, в производственной сборке его нет по построению (см. ниже).

## Стек

Не классический Next: `package.json` зовёт **vinext** (Next-совместимый App Router поверх Vite), сборка — Vite 8 + `@vitejs/plugin-rsc`, хостинг — Cloudflare Workers через `@cloudflare/vite-plugin`. Пакет `next` в зависимостях нужен только ради API: `Metadata`, `notFound`, `next/font`, `next/navigation`.

Tailwind подключён (`@import "tailwindcss"` в `app/globals.css`), но не используется: вся вёрстка на своих классах, из Tailwind реально работает только preflight-ресет.

## Данные

- `public/data/catalog.json` — **единственный источник по артикулам**, тот же файл, что на рабочем сайте. Лежит в `public/`, а не в `app/`, специально: так его одновременно и статически импортирует приложение (`app/data/catalog.ts` тянет `../../public/data/catalog.json`), и читает редактор по HTTP с `/data/catalog.json`, и пишет туда же через File System Access API.
- `app/data/materials.ts` — 9 материалов: категория, `tempMin`/`tempMax` числом, среды, нагрузки, формы, свойства/применение/ограничения. По нему работают фильтры и сравнение. Правится только руками, форм в редакторе для него нет.
- Связка двух моделей — по слагу, через `sourceCodeBySlug` в `app/data/catalog.ts`. Сейчас таблица пустая: единственное расхождение (`pe-hd` → `pe`) ушло вместе с PE-HD, но механизм оставлен — слаг сайта и код поставщика снова могут разойтись. Обратное направление экспортируется оттуда же как `siteSlugBySourceCode` — его берут страница марки и `sitemap.ts`, чтобы связка не расползлась по трём копиям.
- `app/data/site.ts` — адрес сайта одной строкой, используется в `metadataBase`, `robots.ts`, `sitemap.ts` и в абсолютных ссылках Open Graph. Переопределяется переменной окружения `SITE_ORIGIN`, чтобы превью-сборку можно было выложить, не отправляя краулеров на боевой домен. Обращение к `process` там закрыто проверкой `typeof`: модуль попадает и в клиентский граф.

**Каталог править только атомарной записью.** `public/data/catalog.json` импортируется в приложение, поэтому за ним следит Vite. Запись «поверх» (`open(path, "w")` в Python, `> file`, `writeFileSync` в существующий файл) сначала обнуляет файл и лишь потом наполняет его; если watcher успевает прочитать его в этот момент, на странице всплывает оверлей `[plugin:builtin:vite-json] EOF while parsing a value at line 1 column 0`. Данные при этом целы — Vite просто прочитал пустой файл, и оверлей висит до следующей удачной пересборки. Готовый способ: `node tools/write-catalog.mjs <файл-с-новым-json>` (или `-` для stdin) — пишет во временный файл рядом и переносит переименованием, попутно отклоняя неразбираемый JSON, каталог без непустого `materials` и ссылки на несуществующие фото. Редактору это не нужно: File System Access API пишет через swap-файл и подменяет оригинал только на `close()`.

Редактор живёт в `tools/editor` и раздаётся только dev-сервером, поэтому читает и пишет он один и тот же `public/data/catalog.json`. Раньше редактор лежал в `public/` и попадал в сборку — там `/data/catalog.json` отдаётся уже копией из `dist/`, а сохранение шло в `public/`, и правка выглядела пропавшей до пересборки. Теперь такой ситуации не возникает: на `pnpm start` редактора просто нет.

## Редактор каталога

`tools/editor/` — перенесён с рабочего сайта почти без изменений: дерево материалов и артикулов, drag&drop, формы, живое превью через `renderProductInto` из `render.js` (это бывший `js/catalog.js` рабочего сайта).

Что поменяно при переносе:
- читает `/data/catalog.json` (абсолютный путь: сама страница лежит в `/editor/`);
- сохраняет в `<папка проекта>/public/data/catalog.json` — в `editor.js` добавлен спуск в `public/` перед `data/`;
- раздаётся плагином `devEditor()` из `vite.config.ts` с `apply: 'serve'`: в производственную сборку не попадает, наружу не торчит, выход за пределы папки закрыт;
- добавлен хелпер `assetUrl()` в `render.js`: пути к фото в каталоге относительные (`assets/photos/...`), а страница открыта из `/editor/`, поэтому без префикса `/` браузер искал бы их в `/editor/assets/...`.

Открывается и как `/editor/`, и как `/editor/index.html` — плагин отдаёт `index.html` на оба варианта.

Сохранение через `showDirectoryPicker` работает так же, как на рабочем сайте: папка проекта подключается один раз и запоминается в IndexedDB. **При выборе папки указывать корень `exapolymer-next`**, а не `public` — редактор сам спустится в `public/data/`.

Ссылки внутри превью погашены (`makePreviewLinksInert`): превью рисует разметку страницы вместе с её навигацией, и клик по «Оставить заявку» или по карточке артикула увёл бы со страницы редактора вместе со всеми несохранёнными правками. Триггеры лайтбокса исключены — лайтбокс берёт путь к фото из `href`.

## Что накачено с рабочего сайта

- **Форма заявки** — POST на web3forms тем же эндпоинтом и ключом, что на `exapolymer.ru`. Было: только `mailto:`, то есть заявка уходила лишь при настроенном почтовом клиенте. `mailto` оставлен запасным путём в ветке ошибки. В отличие от обработчика на рабочем сайте, стили ошибки не залипают — там они выставлялись инлайном и не сбрасывались, из-за чего удачная повторная отправка показывалась красным.
- **`robots.ts` / `sitemap.ts`** — 43 URL (5 статических, 9 материалов, 29 марок). В исходном проекте от GPT не было ни того, ни другого.
- **`app/icon.svg`** — иконка вкладки. `public/favicon.svg` лежал мёртвым: Next подхватывает только `app/icon.*`, а поля `icons` в метаданных не было.
- **Домен** — `metadataBase` переведён с адреса предпросмотра `chatgpt.site` на `exapolymer.ru`.
- **Навигация** — `/about` и `/supply` в исходнике не имели ни одной входящей ссылки; добавлены в шапку и подвал. `/request` дублировал `/contacts` той же формой и текстом — заменён постоянным редиректом.
- **Лента материалов** (`app/components/material-nav.tsx`) — полоса со всеми 9 материалами под hero страницы материала и страницы марки, активный подсвечен, справа ссылка «Сравнить материалы» на `/catalog`. Заменила две ссылки «назад» (`← Каталог материалов` и `← Все марки PEEK`), которые вели на один шаг вверх и занимали место в шапке hero, и ссылку «Сравнить материалы» из заголовка секции «Доступные позиции» — та вела туда же, куда теперь ведёт лента. Ссылка «Все марки →» в секции «Другие исполнения» внизу карточки марки оставлена. Верхние отступы обоих hero увеличены, чтобы компенсировать удалённую строку.
- **`og-milk.jpg`** — актуальная OG-картинка (фото листов пластика). Прежний `og.jpg` (92 КБ, оптимизация исходного `og.png` на 1206 КБ) удалён как неиспользуемый — везде в метаданных теперь `og-milk.jpg`.

## Чем этот проект отличается от рабочего сайта

Данные разошлись в трёх местах. Марки POM: здесь их 7 против 4 на рабочем сайте, марки PET-P: 3 против 1; PTFE, PVDF, PP, PE-HD и PE-UHMW, наоборот, убраны целиком — 9 материалов против 14 (29 марок против 25 всего) — см. ниже. Фотографии: 73 против 50, добавлены снимки трёх марок PA и всех трёх марок PET-P.

**Фото PA** взяты из черновой папки пользователя `Сайт инженерных пластиков\Фото\PA\<марка>\`: файл в корне папки марки → `photo`, содержимое «Примеры работ» → `workPhotos`. Сжаты по тому же правилу, что и остальные (ширина ≤ 1400 px, JPEG q82), лежат в `public/assets/photos/pa/`. Два исходника намеренно **не** взяты: `A6612N\Примеры работ\640-Photoroom-2` — с чужим водяным знаком (китайский WeChat-аккаунт в углу), `AG12B\Пример работ\M12B-4` — попиксельно тот же кадр, что уже опубликован под POM `M12B` как `m12-work-6.jpg`. Остальные файлы в папке `AG12B` тоже названы `M12B-*` / `M6B-*`, то есть имена достались от POM; по содержимому это другие детали, но принадлежность к PA+GF30 стоит подтвердить у поставщика.

### Пять материалов убраны из каталога

По решению пользователя с сайта сняты целиком фторполимеры и полиолефины: `ptfe`, `pvdf`, `pp`, `pe-hd` и `uhmwpe` удалены из `app/data/materials.ts`, а материалы `ptfe` (марка `F6B`), `pvdf`, `pp`, `pe` и `uhmwpe` (все без марок, кроме PTFE) — из `public/data/catalog.json`. Осталось 9 материалов; страницы удалённых отдают 404, из карты сайта они ушли.

Что пришлось поправить следом, потому что материалы были вписаны в тексты руками: витрина на главной (`peek, ptfe, pom` → `peek, pom, pa`), список материалов в подвале (ссылка PTFE заменена на PA, счётчик «Все 14 материалов» → «Все 9»), описания в метаданных `/catalog` и `layout.tsx` (в них поимённо стояли PTFE и UHMWPE), плейсхолдер поиска («PEEK, фторопласт…» → «PEEK, полиацеталь…») и группы материалов в превью редактора (`tools/editor/render.js`: из «Высокотемпературных» ушли ptfe и pvdf, группа «Стандартные» удалена целиком). Из фильтров сама собой пропала среда «УФ / улица» — её заявлял только PVDF; опции считаются из данных, поэтому правок не потребовалось. Упоминание PTFE осталось там, где оно про наполнитель, а не про материал каталога: марка POM `MF12` (POM+PTFE).

Данные не потеряны — они в истории git до этого коммита.

### PET-P разложен на три марки производителя

Была одна позиция `T12` (белый/чёрный, общая таблица NAGOMER). Стало три — как в [категории PET на nagomer.com](https://nagomer.com/category/nagomer-product-centre/pet/):

- **PET-P** — карточка `NGM-PETP`, «Wind Energy Special»: только лист 1250×2020 мм, толщины 18 / 21,5 / 25 мм, натуральный.
- **T12B** — чёрный, лист 620×2020 (6–50 мм) и 1250×2020 (12–35 мм), стержень Ø15–100 мм.
- **T12N** — натуральный, лист 620×2020 (6–10 мм) и 1250×2020 (12–100 мм), стержень Ø15–210 мм.

Общая таблица физсвойств NAGOMER (4 группы) осталась одинаковой у всех трёх — в исходнике она дана одной колонкой `T12N/B` на обе марки. Сверх неё у T12B и T12N добавлена пятая группа — **протокол испытаний NOEGEM** (`NGM202503010-01` от 10.03.2025 и `NGM20250203-01` от 03.02.2025), разобранный с картинок в табе «Physical parameters». Группы намеренно не смешаны: протокол даёт другие значения тех же показателей (плотность 1,39 против 1,37; прочность 78,9 / 89,4 против 85,9; Изод без надреза 40,1 / 55,1 против 12 с надрезом) плюс уникальные — сжатие и сдвиг.

Что в источнике противоречиво и подтверждается у поставщика: в обоих протоколах единица прочности при сдвиге указана как °C (в каталоге записана МПа, оговорка стоит в поле «Условия»); в протоколе T12N замеры растяжения 110,5 / 109,9 / 110,3 не сходятся с итогом 89,4, а замеры удлинения 1,8 / 2,3 / 1,9 — с итогом 13 %; натуральный цвет описан как «янтарно-прозрачный», а на снимках производителя лист молочно-белый.

Фото — 11 файлов в `public/assets/photos/pet/`, из черновой папки пользователя `Материалы сам скачал\PET\<марка>\`. Кадр `NGM-T12B-12` взят один раз (в исходнике лежал в двух размерах). Снимки для PET-P названы `T12N-*`: у производителя они на карточке PETP, материал тот же натуральный PET. Примеры работ у T12N позже заменены на два кадра из `Фото\PET\T12N\Примеры работ` — те же детали, но с убранными бирками NOEGEM; было три снимка с сайта производителя.

### POM пересобран по документам производителя

Три источника, все в папке `Cloude\`:

- `NAGOMER_Physical_Property_Table.xlsx` — 27 строк физических свойств по столбцам-маркам. Столбцы всех материалов кроме POM в файле скрыты.
- `таблица размеров пластика.xlsx` — что производитель реально катает: марка × форма × формат листа × толщина (в ячейках масса стандартного листа/прутка). Строки не-POM скрыты.
- Карточки товара на `nagomer.com` — маркетинговые описания: [M6N](https://nagomer.com/elementor-27458/), [M6B](https://nagomer.com/elementor-27628/).

Было четыре сборных марки, стало семь:

| Было | Стало | Столбец в property-table | Строки в таблице размеров |
| --- | --- | --- | --- |
| `M12` (белый/чёрный/цветной, цифры от чёрного) | `M12N` — POM-C, натуральный | F | 1–4 |
| | `M12B` — POM-C, чёрный | G | 5–8 |
| `M12H` | `M12H` — POM-H | H | нет |
| `M6` (цифры от чёрного) | `M6N` — ESD-POM, бежевый | I | 9–11 |

| | `M6W` — ESD-POM, белый | J | 15–16 |
| `MF12` | `MF12` — POM+PTFE | L | нет |

Разбиение ESD-POM на три марки подтверждается плотностями: 1.376 / 1.386 / 1.384 в столбцах I / J / K property-table совпадают с M6N / M6W / M6B в таблице размеров. Отдельно сверено с протоколом испытаний `NGM20250321014` (PDF со страницы M6N): все семь измеренных им показателей совпали со столбцом I.

Размерные сетки у `M12N`, `M12B`, `M6N`, `M6B`, `M6W` собраны скриптом из таблицы размеров, а не выдуманы: показывается ровно та толщина и тот формат листа, под которые у производителя есть масса. `M12H` и `MF12` в таблице размеров отсутствуют — сетки у них так и остались пустыми.

Числа на карточках `nagomer.com` местами расходятся с property-table (страница M6B обещает −40…+100 °C и 10⁶–10⁹ Ω против −30 °C и 10⁶–10⁸ Ом·см в таблице). В описаниях оставлены значения из таблицы, чтобы текст не спорил с таблицей параметров на той же странице. Обе страницы M6N и M6B ссылаются на один и тот же PDF — бежевый; у чёрной марки datasheet на сайте производителя перепутан.

Фотографии поделены по цвету: `m12-photo` + белые изделия → `M12N`, чёрные → `M12B`; `m6-photo` + бежевые изделия → `M6N`, чёрные → `M6B`. У `M6W` фото нет.

Из-за переименования старые адреса `/materials/pom/m12` и `/materials/pom/m6` больше не открываются. Сайт никуда не выложен, редиректов нет; если марки поедут в прод — их надо будет добавить.

Разное — подача. Здесь: серверный рендер и статическая генерация вместо сборки страниц на клиенте, отдельный URL у каждой марки (`/materials/peek/k12n-b` против `product.html?m=peek&a=K12N/B`), 4 вкладки на карточке, честные пометки «уточняется по запросу» вместо обещаний наличия.

## Что не сделано

- Живое превью в редакторе показывает **старый дизайн** рабочего сайта, а не эти страницы. Чтобы совместить, нужно собирать превью из React-компонентов — то есть переписать превью, а не перенести.
- `materials.ts` правится только руками: новый материал через редактор попадёт в `catalog.json`, но без записи в `materials.ts` не появится ни в каталоге, ни в фильтрах.
- На 18.09.2026 у всех 29 марок есть главное изображение и галерея; 9 ранее пустых марок дополнены существующими ИИ-иллюстрациями с явными подписями (см. `IMAGERY.md`). У 9 марок нет подтверждённой размерной сетки. Дисциплина прежняя: **не выдумывать цифры**, при отсутствии источника оставлять пусто и говорить об этом.
- В `catalog.ts` две правки данных живут в коде, а не в данных: regex чинит «полифениленсульфона» → «полифениленсульфида», и целиком подменяется описание PPS **S12B** (в каталоге поставщика туда попал текст от SG12+GF40 — про 40 % стекловолокна в базовой чёрной марке). Правильнее починить в `catalog.json` и убрать костыли.
- **Переходы между страницами — полной перезагрузкой.** Внутренняя навигация намеренно на `<a>`: клиентский роутер vinext 1.0.0-beta.3 нерабочий. Проверено на `<Link>`: в dev переход падает с «process is not defined» (`stageAppNavigationFailureTarget`), в производственной сборке — «TypeError: e is not a function» в `link-*.js`, причём обработчик успевает отменить событие, и ссылки становятся **мёртвыми**. Симптомы в dev и в проде разные, поэтому проверять обязательно на `pnpm build` + `pnpm start`. Вернуться к `<Link>` — когда vinext починит; правило `@next/next/no-html-link-for-pages` до тех пор выключено в `eslint.config.mjs` с этим обоснованием.
- `next/image` не используется осознанно: загрузчик не настроен, а на Cloudflare Workers встроенный оптимизатор не работает. Фото уже сжаты, с `width`/`height` и `loading="lazy"`. Правило `@next/next/no-img-element` выключено там же.
